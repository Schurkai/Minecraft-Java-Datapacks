# 감사 보고서

## 기준

Mojang의 2026-06-16 Java Edition 26.2 정식 릴리스와 공식 서버 JAR을 기준으로 삼았다. JAR SHA-1은 `823e2250d24b3ddac457a60c92a6a941943fcd6a`이며 내부 `version.json`은 `stable=true`, 데이터팩 107.1, 리소스팩 88.0이다.

## 데이터와 호환성

- v0.1의 바닐라 `armor`, `bow`, `crossbow`, `damage` 배타 태그 빈 전체 오버라이드를 제거했다. 요구한 조합만 개별 인챈트와 좁은 Toybox 태그로 완화했다.
- 26.2 생성 데이터와 바닐라 인챈트 오버라이드를 필드 단위 비교했다. 대부분은 의도한 `max_level`/`exclusive_set`만 바꾸며, RC4의 폭발 보호는 레벨 VII 이상에서 넉백 저항 1.0이 되어 폭렬 반동을 완전히 없애는 문제를 막기 위해 해당 attribute 값만 최대 0.8로 추가 제한한다.
- 바닐라와 완전히 같던 `breach.json` 오버라이드를 삭제했다.
- `exclusive_set` 미기재의 공식 기본값이 빈 집합임을 bytecode로 확인했다. 보호 4종, 수선/무한, 다중 발사/관통의 불필요한 `#toybox:exclusive_set/none`을 필드와 태그 모두 삭제해 외부 팩의 태그 추가 위험을 없앴다.
- 공식 호환성 검사가 양쪽 인챈트 집합을 대칭 검사함을 확인했다. 피해 3종끼리는 허용하면서 찌르기·밀도·격파와의 제한은 유지된다.
- 폭렬은 순수 인챈트 JSON만으로 투사체별 가변 카운터를 안전하게 감소시킬 수 없어, 폭렬과 다중 발사·관통을 배타로 묶는 축소안으로 폭발 상한을 보장했다. 일반 다중 발사+관통은 계속 허용된다.

## 함수와 아이템

- `crafting_transmute`, `minecraft:glider`, 플레이어 입력 predicate, `minecraft:apply_impulse`, 커스텀 인챈트 효과가 26.2 로더에서 수용된다.
- 26.2 `TransmuteRecipe.matches`는 결과가 입력과 같은 재결속을 거부하고 입력 컴포넌트를 결과에 보존한다. 다이아 결속→네더라이트 업그레이드→재결속은 이름 차이 때문에 별도 경계 사례로 남겼다.
- 공식 `hit_block` 문맥의 `this`가 투사체, `origin`이 충돌 좌표이고 `run_function` 실행 주체도 투사체임을 bytecode로 확인했다.
- 합성 화살/소유자 스모크로 `execute on origin`이 소유자로 전환하면서 충돌 위치를 보존함을 실제 서버에서 확인했다. 실제 플레이어 이동 감각은 별도 수동 항목이다.
- 기존 갈고리 사격은 32블록을 허용하면서 30틱×0.65=19.5블록밖에 이동하지 못했고 모든 활 빗맞힘을 이동 입력으로 소비했다. 전용 `minecraft:fishing_rod` 도구로 분리하고 찌의 `projectile_spawned` 사건에서 소유자를 연결했다.
- 데이터팩은 새 아이템 ID를 등록할 수 없으므로 갈고리의 실제 ID는 낚싯대다. 제작 결과의 `custom_data`는 식별·표시용이고 실제 발동 조건은 `toybox:grappling` 인챈트다. 기본 `tripwire_hook` 아이템 모델을 사용하므로 핵심 기능과 외형에 리소스팩이 필요 없다.
- 공식 낚싯찌는 소유자와 32블록을 넘으면 스스로 제거된다. 갈고리는 활성 플레이어만 32블록 안의 제한된 찌 집합을 조회한 뒤 소유자 ID가 일치하는 자기 찌만 처리한다. 이 순서로 가까운 다른 플레이어의 찌 때문에 자기 갈고리가 취소되는 경쟁 조건을 피한다. 찌 반경에 맞춘 ±0.16블록 6방향/바닥 접촉으로 걸림을 판정하며, 공중 정점이나 열린 공간의 몹 걸림은 블록 접촉이 없어 제외된다.
- `탄성`의 `minecraft:bounciness`는 낙하 후 튕김이라 사용자가 기대한 점프 높이 조절과 달랐다. 26.2의 플레이어 `input.jump` predicate와 상승 중 `apply_impulse`로 교체해 키를 놓는 즉시 추가 추진이 끝나게 했다. 저장된 장비 호환을 위해 레지스트리 ID는 바꾸지 않았다.
- 균열 사격은 웅크리기·8–48블록·12점 빈 공간·60틱 cooldown을 요구하며, 성공 후 `minecraft:ender_pearl` 피해 5와 느린 낙하를 적용한다.
- 블록에 박힌 화살의 `hit_block` 위치는 공식 구현에서 맞은 블록 안쪽으로 아주 조금 clamp된다. 기존 폭렬은 폭발 중심도 고체 내부여서 지면의 `seenPercent`가 0이 될 수 있었고 `damage_type`도 빠져 있었다. 위쪽 0.25 오프셋과 폭발 피해 유형을 추가했다.
- 26.2 `ExplodeEffect.attribute_to_user`는 인챈트 소유자가 아니라 효과의 affected 엔티티를 source로 삼는다. 직격 `post_attack`의 affected를 피해자에서 직격 화살(`damaging_entity`)로 바꾸고 블록/직격 모두 `true`를 사용했다. 폭발에서 제외되는 것은 화살뿐이라 피해자와 사수는 계산에 포함되며, 화살 소유자를 통한 PvP·팀 피해 검사도 유지된다. 다만 폭발만으로 난 처치의 통계·사망 메시지가 사수에게 완전히 귀속되지는 않을 수 있다.
- 고정 +Y 오프셋은 지면 윗면 수정이다. 벽·천장 모든 면의 반동을 보장하지 않으며 실제 클라이언트 물리는 수동 시험 항목으로 남겼다.

## v0.4 고등 마법부여 감사

- 26.2 공식 레지스트리에 `minecraft:default_block_use` 발전 과제 트리거가 존재하며, 마법부여대 블록 조건을 붙인 발전 과제에서만 진입한다. 매 틱 테이블·플레이어·아이템을 검색하지 않는다.
- 발전 과제 보상 함수는 클릭 블록 좌표를 직접 받지 못한다. 구현은 사건이 마법부여대 사용임을 먼저 증명한 뒤 플레이어 눈에서 0.25블록 간격, 최대 5.25블록의 짧은 시선 추적으로 테이블 좌표를 복원한다. 이 UX의 실제 면·거리 성공률은 라이브 클라이언트 수동 시험 전이다.
- 26.2 플레이어 아이템 직렬화에서 보조 손은 `Inventory[{Slot:-106b}]`, 책 인챈트는 `components."minecraft:stored_enchantments"`, 주 손 인챈트는 `SelectedItem.components."minecraft:enchantments"`에서 읽는다. compound의 `data get` 결과로 키 수가 정확히 1인지 검사하고 지원 ID를 고정 분기한다.
- 기존 동일 인챈트에는 `/enchant`가 적합하지 않으므로 결과 ID·레벨별 `minecraft:set_enchantments` 아이템 수정자 59개를 사용한다. `add:false`는 지정 ID의 레벨을 절대값으로 바꾸며 다른 인챈트를 지우지 않는다. 개발 스모크는 날카로움만 V→VI로 바꾼 뒤 내구성 III, `repair_cost`, `custom_data`가 유지되는지를 검사하도록 구성했다.
- 지원 범위는 보호 4종 V–X, 날카로움·강타·살충·힘·찌르기 VI–X, 효율·밀도 VI–VII, 행운·약탈·내구성 IV–V다. 같은 ID·같은 현재 레벨의 단일 책을 요구하므로 정상 생존 아이템에 새로운 배타 조합을 추가하지 않는다. 명령으로 만든 비정상 아이템의 기존 호환성은 교정하지 않는다.
- 바닐라 내부 책장 power 계산은 임의의 확장 반경에 재사용할 수 없어 60개 고정 슬롯을 명시했다. 반경 2의 두 높이 32개, 반경 3의 테이블 높이 24개, 반경 3 한 칸 위의 동서남북 4개이며, 각 슬롯과 중앙 사이의 1–2개 통로도 transmitter/provider 태그인지 검사한다.
- 책장 기준은 결과 IV/V 15, VI 24, VII 32, VIII 40, IX 48, X 60개다. 비용은 결과 레벨 `L` 기준 경험치 `4+2L`, 청금석 `ceil(L/2)`, 자수정 `max(0,L-5)`, 보조 손 책 1권이다. 희귀도 계수와 관리자 비용 배율은 구현하지 않았다.
- 모든 조건과 재료 수를 먼저 검사하고 `item modify` 성공 뒤에만 책·재료·경험치를 소비한다. 전역 fake-player 점수는 사용하지만 하나의 발전 과제 보상 함수가 주 스레드에서 동기적으로 끝나므로 이벤트 사이에 중간 상태가 섞이지 않는다.

## v0.4 포션 합성 감사

- 양조기 `minecraft:default_block_use` 발전 과제가 사건 진입점이다. 일반·투척용·잔류형 포션을 양손에 들었을 때만 동기 함수가 실행되며 틱 검색, 드롭 아이템, 전용 컨테이너, marker/interaction 엔티티는 없다.
- `potion_contents.potion`의 공식 기본 포션을 명시적 효과 목록으로 펼친 뒤 `custom_effects`와 합친다. 허용 목록은 26.2의 바닐라 효과 ID 40개이며, 알 수 없는 ID, 한 병 안의 중복 ID, `hidden_effect`, I–V 밖의 amplifier, 1–72,000틱 밖의 duration은 거부한다.
- 공식 `strong_turtle_master`에는 amplifier 5인 VI 감속이 포함되므로 Toybox의 입력·출력 최대 V 정책에 따라 거부한다. 이는 누락이 아니라 명시적 상한 처리다.
- 같은 단일 효과의 단계 상승은 같은 amplifier I–IV 두 병과 발광석 전용 모드를 요구한다. 결과는 한 단계 상승하고 시간 효과는 짧은 쪽의 75%, 즉시 효과는 1틱이다. 시간 연장은 단계 차 1 이하에서 낮은 단계를 사용해 시간을 더하고 72,000틱에서 제한한다.
- 서로 다른 효과 합집합은 양쪽 ID가 하나도 겹치지 않을 때만 최대 5종을 허용한다. 반대 성격의 서로 다른 ID는 자동 상쇄하지 않는다. 한 ID라도 겹친 다중 효과 입력은 모호한 병합을 피하기 위해 거부한다.
- 병 형태는 일반 < 투척용 < 잔류형의 최댓값이다. 투척용 승격은 화약 1개, 잔류형 승격은 드래곤의 숨결 1개를 요구하며 잔류형으로 바로 갈 때 화약을 중복 요구하지 않는다.
- 효과 점수는 `(amplifier+1)^2 × max(1,floor(duration/1200))`, 경험치 비용은 합계 `S`에 대해 `3+ceil(2×sqrt(S))` 레벨이다. 같은 효과 단계 상승의 발광석은 결과 II–V에 1–4개, 시간 연장의 레드스톤은 결과 18,000틱당 올림하여 1–4개다. 자수정은 같은 효과에서 1개와 결과 III 이상 추가 1개, 합집합에서 결과 효과 수와 입력 III 이상 효과 수의 합이다.
- 결과는 고정 보라색, 번역 가능한 `혼합 물약` 이름과 `toybox.mixed_potion` 표식을 가진 새 아이템이다. 입력 이름·lore·사용자 색·기타 비효과 컴포넌트는 보존하지 않는 정책이다.
- 결과 item component 매크로 적용 성공을 확인한 뒤 보조 손 병과 비용을 소비한다. 임시 `toybox:scratch alchemy` storage는 함수 시작과 끝에서 삭제된다. 공식 서버 스모크에는 기본 포션 정규화, IV→V, 72,000틱, 공식 VI 거부, 5효과 상한, 세 병 형태 결과 생성을 검사하는 항목을 추가했지만, 실제 음용·투척·잔류 구름과 2인 클릭은 라이브 클라이언트 시험 전이다.

## v0.4.0-rc2 라이브 클라이언트 수동 키트 감사

- `/function toybox:dev/client_test_kit`은 일반 플레이 진입점이 아닌 명시적 개발 함수다. 틱 호출 그래프나 발전 과제에서 호출되지 않고 `schedule function`도 사용하지 않으므로 설치만으로 Realm의 상시 처리량을 늘리지 않는다.
- 키트는 실행자의 수평 시선 기준 전방 8블록을 정렬한 위치에 마법부여대, 고정 슬롯 책장 60개, 양조기를 모두 `setblock ... keep`으로 배치한다. 설치 뒤 실제 고등 마법부여 계수 함수를 호출해 활성 책장 수를 표시하므로 `60/60`이 아니면 시험을 중단하고 열린 공간으로 옮겨야 한다.
- 긍정 경로 예산은 날카로움 V→X 5회에 경험치 100레벨·청금석 21개·자수정 15개, 신속 강도 합성에 53레벨·자수정 2개·발광석 4개, 신속 시간 합성에 65레벨·자수정 2개·레드스톤 4개·화약 1개, 5효과 합집합에 9레벨·자수정 5개·드래곤의 숨결 1개다. 합계 경험치 227레벨, 청금석 21개, 자수정 24개가 정상 순서에서 정확히 0이 되는 경계 검사를 의도한다.
- 같은 효과 합성의 발광석·레드스톤 동시 소지 거부를 피하기 위해 본 키트는 두 가루를 기본 지급하지 않고 강도/시간 단계별 함수로 각각 4개만 지급한다. 별도 거부 입력은 공식 `strong_turtle_master`와 신속 병이며, 병·재료·경험치가 소비되지 않아야 한다.
- 테스트 장비는 날카로움 V와 내구성 III, 손상 37, 수리 비용 17, 사용자 이름·설명·시험 표식을 포함한다. 키트가 직접 확인해 주는 것은 아니므로 사용자가 X 도달 뒤 모든 비대상 컴포넌트를 눈으로 검사하고 결과를 기록해야 한다.
- 키트는 실행자의 경험치 레벨과 점수를 0으로 만든 뒤 227레벨을 지급한다. 빈 인벤토리와 폐기 가능한 열린 시험 월드가 필수이며, 생존 월드에서 안전하게 되돌릴 수 있는 트랜잭션이나 백업 기능이 아니다.
- 정리는 플레이어가 시험 마법부여대 바로 위에 섰을 때만 발밑 테이블을 원점으로 실행한다. 영속 marker와 `@e` 검색을 모두 제거해 잔존 엔티티와 Realm 틱 비용이 없다. 원점 슬롯에 그 시점에 같은 종류의 책장·마법부여대·양조기가 있으면 제거하므로 원래 있던 블록이나 시험 중 새로 놓은 같은 블록을 출처별로 구분하지 못한다. 다른 위치에서 실행하면 구조물은 남고 태그가 붙은 미사용 입력만 지운다.
- 정리 함수는 `toybox.client_test` 태그가 남은 지정 종류의 아이템을 지운다. 고등 마법부여가 시험 검의 `custom_data`를 보존하므로 X까지 강화된 검도 정리 시 삭제된다. 반대로 새 혼합 물약은 입력의 시험 태그를 보존하지 않아 남으며, 던진 물약 효과와 지급·소비된 경험치도 제거하거나 복원하지 않는다. 자동 로그아웃 정리도 없다.
- 리그 설치·60책장 계수·정리용 공식 서버 스모크와 정적 검증 규칙이 추가됐지만, 이는 실제 마우스 클릭, UI, 음용·투척, 입력감, 2인 동시성 또는 Realm 업로드를 통과했다는 뜻이 아니다. 실제 클라이언트와 Realm 시험은 아직 실행하지 않았다.
- RC2는 개발용 함수와 번역·문서·검증 범위만 추가하며 저장되는 gameplay state, objective, 마이그레이션 스키마를 바꾸지 않는다. 따라서 사용자에게 보이는 릴리스 표시는 RC2지만 데이터 버전은 400을 유지한다.

## v0.5 줄자·분필 감사

- 다음 우선 후보였던 소모성 특수 화살은 플레이어가 활·쇠뇌로 발사했을 때 탄약의 `custom_data`가 투사체까지 보존되는지 실제 클라이언트에서 확인하는 G0가 남아 있다. 헤드리스 서버에서 명령으로 만든 투사체는 이 경계를 증명하지 못하므로 기능을 되는 것처럼 구현하지 않았다.
- 줄자는 전용 아이템을 흉내 내지 않고 명시적 `/trigger tb_measure`만 사용한다. 시작 좌표·차원·상태는 플레이어 objective에, 계산 scratch는 한 함수 호출에서 끝나는 fake player에 저장한다. 계산 함수는 틱 경로에 없다.
- 거리 제곱은 signed 32-bit scoreboard 범위 안에 있어야 한다. 각 축을 26,000으로 제한하면 세 축 제곱 합 최댓값은 2,028,000,000으로 2,147,483,647보다 작다. 직선거리는 0..46,340 구간을 16회 상향 중간값 이진 탐색해 정확한 내림 제곱근을 얻는다.
- 시작과 끝은 오버월드·네더·엔드의 같은 차원이어야 한다. 지원하지 않는 차원, 차원 불일치, 거리 초과는 결과를 만들거나 시작점을 지우지 않으므로 사용자가 원래 차원으로 돌아가거나 명시적으로 취소할 수 있다.
- 분필은 플레이어별 8개 슬롯의 정수 좌표·차원을 objective로 저장한다. 슬롯은 데이터팩이 로드된 동안 재접속·`/reload`·서버 저장/재시작에 영속하지만, 실제 클라이언트 재접속 절차는 아직 실행하지 않았다.
- 표시 시작은 `/trigger tb_chshow`, 지속 처리는 `tb_cshow=1..`인 플레이어만 최대 100틱 실행한다. 세 바닐라 차원에 명시적으로 `execute in`하고 `particle ... force @s`를 사용해 요청자 한 명에게만 세 점을 전송한다. 차원이 달라지면 표시를 중단한다.
- 분필 좌표를 함수 매크로에 넘기는 `toybox:runtime chalk_marker`는 동기 호출 직전에 만들고 모든 슬롯 함수에서 직후 제거한다. `summon`, marker/interaction, 예약 함수, 강제 청크 로드, 블록 변경은 없다. 같은 서버 틱의 플레이어 실행은 명령 주 스레드에서 순서대로 끝나므로 scratch가 호출 사이에 남지 않는다.
- 정적 검증과 공식 26.2 서버 소스 시험에서 v0.5 objective/마이그레이션, 세 차원 판별, 제곱근 경계와 전체 스모크 집계 0을 확인했다. 실제 클라이언트의 좌표 표시·입자 가시성·2인 동시성·Realm 업로드는 통과로 기록하지 않는다.

## v0.7 수프 냄비 감사

- 데이터팩은 가마솥 블록 자체에 사용자 데이터를 저장할 수 없다. 물 가마솥 level로 회분을 위장하면 양동이 상호작용과 충돌하므로, 빈 가마솥 중심의 `minecraft:marker`에 종류와 회분만 저장한다. 서버 전체 상한은 64개다.
- 수프 한 개를 네 개로 늘리는 초기 설계를 폐기했다. 등록 입력과 최종 출력은 같은 바닐라 수프 4개이며 추가 효과·사용자 음식 컴포넌트를 만들지 않는다. 일반·투척·잔류 같은 별도 형식도 없으므로 핵심 기능에 리소스팩이 필요 없다.
- 등록은 구조, 기존 marker, 주 손 종류, 인벤토리 수량, 64개 상한을 먼저 검사한다. marker 소환 확인 뒤에만 `clear ... 4`를 실행하고 예상 밖의 부분 제거 1–3개는 즉시 같은 바닐라 아이템으로 돌린다. 모든 명령은 한 트리거 함수 안에서 동기적으로 끝난다.
- 지급은 인벤토리 빈칸 수를 추측하지 않고 빈 주 손을 요구한다. `item replace` 성공을 점수로 확인한 뒤에만 marker의 회분을 1 줄이고, 0이 되면 같은 함수에서 marker와 전역 개수를 제거한다. 서버 명령은 한 스레드에서 순서대로 실행되므로 같은 마지막 회분의 두 요청이 중간 상태를 공유하지 않는다.
- 사용 시에는 플레이어 눈에서 0.25블록 간격의 21지점, 최대 5.25블록만 검사하고 대상 블록 0.9블록 안의 marker 하나만 선택한다. 모든 냄비를 매 틱 찾지 않는다. 5분마다 로드된 `toybox.soup_pot` 최대 64개만 검사해 가마솥이나 일반 모닥불이 사라진 고아 marker를 제거한다.
- 꺼진 일반 모닥불은 구조를 보존하되 지급을 막는다. 가마솥·모닥불 파손은 아이템을 환불하지 않아 블록 파괴 복제를 막는다. 언로드된 청크는 다음 로드 뒤 유지보수 주기에 정리된다.
- 기본 아이템 ID만으로 수량을 세므로 이름·설명·`custom_data`가 붙은 같은 수프를 넣으면 평범한 바닐라 수프로 정규화될 수 있다. 임의 컴포넌트가 있는 네 개의 동일 아이템을 명령만으로 안전하게 복제해 출력하는 일반 해법은 이번 범위에서 사용하지 않았고 사용자 지정 수프 비지원으로 문서화했다.
- 첫 개발 스모크는 새로 강제 로드한 먼 청크에 marker를 소환하고 같은 함수 호출 안에서 즉시 전역 selector로 찾을 수 있다고 가정해 구조 2/2인데 marker 0인 거짓 실패를 냈다. 실제 플레이어 요청처럼 엔티티가 이미 틱 중인 스폰 청크로 시험 좌표를 옮겼고, 구조 2/2·소환 성공 1·marker 1·종류 2·회분 4·마지막 제거 뒤 총계 0·잔존 0을 공식 서버의 최초 부팅과 재시작에서 확인했다.
- 정적 검증과 공식 26.2 서버 소스 시험은 통과했다. 실제 클라이언트의 시선 정확도, 섭취·그릇 반환, 두 플레이어의 마지막 회분, 64/65개 경계, 청크 언로드와 Realms는 아직 통과로 기록하지 않는다.

## v0.8 측량가 업데이트 감사

- 줄자의 기존 좌표 차이는 이동량이므로 건축 블록 수와 하나 차이 난다. 새 크기·면적·부피는 시작 블록과 끝 블록을 모두 포함해 각 축을 `abs(Δ)+1`로 정의했다. 같은 블록을 두 번 선택하면 `1×1×1`, 바닥 1, 수직 4면 4, 부피 1이 된다.
- 축 차이 26,000 상한에서 각 span은 최대 26,001이고 두 축 곱은 최대 676,052,001이라 signed 32-bit 안이다. 수직 4면은 `2×(X×Y+Y×Z)`의 마지막 배수 전에 1,073,741,823 이하인지 검사한다. 부피는 `X×Y <= floor(2,147,483,647/Z)`를 먼저 검사해 오버플로가 가능한 경우 해당 값만 생략한다. 기존 Δ·직선·맨해튼 결과는 계속 출력한다.
- 분필 나침반은 각 슬롯의 좌표·차원을 동기 함수 매크로로 `minecraft:lodestone_tracker`에 기록한다. `tracked:false`라 실제 자석석 검증과 목표 청크 로딩을 하지 않으며, 세 차원의 resource ID와 좌표는 공식 서버가 직렬화한 실제 아이템 컴포넌트로 확인했다.
- 입력은 주 손의 일반 `minecraft:compass` 정확히 1개, 저장된 정상 슬롯, 자수정 조각 1개를 먼저 요구한다. `SelectedItem.components`가 있는 각인·사용자 지정 나침반은 전체 `item replace`로 기존 데이터를 잃지 않도록 거부한다. 교체 성공 점수가 1일 때만 자수정을 소비하고 scratch storage는 같은 호출 끝에서 제거한다.
- 첫 나침반 스모크는 갑옷 거치대의 장비 NBT를 `HandItems[0]`에서 직접 읽는 가정 때문에 적용 성공을 0으로 오판했다. 실제 `item replace entity ... weapon.mainhand` 성공값을 기록하고, `item replace block ... from entity`로 임시 barrel에 복사한 뒤 표준 컨테이너 `Items` 경로에서 검사하도록 바꿨다. 오버월드·네더·엔드 3개 목표, `tracked:0b`, 좌표, 이름, 설명, 비중첩 값 1과 식별 `custom_data`가 최초 부팅·재시작에서 모두 일치했다.
- 나침반 각인은 trigger 호출 때만 실행되고 기존 분필 좌표 objective를 재사용한다. 새 영속 엔티티·marker·예약 함수·강제 로드·매 틱 좌표 계산은 없다. 다만 플레이어 `SelectedItem.count/components` 선검사와 실제 바늘 렌더링은 헤드리스 서버로 증명할 수 없어 클라이언트 시험 항목으로 남겼다.

## v0.9 수확 낫 감사

- 순수 데이터팩은 새 아이템 ID나 임의 도구의 일반 우클릭 콜백을 등록할 수 없다. 철 괭이에 식별 `custom_data`와 장시간 `minecraft:blocks_attacks` 사용 동작을 붙이고, 해당 아이템의 `minecraft:using_item` 발전 과제만 진입점으로 사용했다. 실제 클라이언트의 사용 자세와 우클릭 감각은 수동 시험 전이다.
- 사건 발생 시 눈에서 0.2블록씩 최대 25회, 총 5블록만 추적한다. 공기 계열에서는 계속하고 첫 비공기 블록에서 멈추며, 완숙 밀 age 7·당근 7·감자 7·비트 3·네더 사마귀 3만 3×3 중심으로 인정한다.
- 각 대상은 `loot spawn ... mine`을 현재 손 문맥으로 먼저 실행한 뒤 공기로 바꾼다. 이 순서로 바닐라 작물 전리품과 행운을 사용하고, 씨앗을 별도로 소비·재배치하면서 생길 수 있는 중복과 부분 실패를 피하기 위해 자동 재파종은 제외했다.
- 성공한 스윕에만 철 괭이 최대 내구도 250 기준 정확히 1이 증가하도록 `minecraft:set_damage`의 잔여 내구도 비율에 `-0.0041`을 더한다. 손상 249는 수정자 적용 전에 명시적으로 제거해 파손을 보장한다. 이 직접 비용은 내구성 인챈트의 확률 감소를 적용하지 않는다.
- 틱 경로는 `toybox.sickle_active` 사용자에게만 최대 10틱 cooldown을 감소시키고 발전 과제를 재무장한다. 작물이나 드롭을 매 틱 찾지 않으며, 한 사용당 상한은 시선 25지점과 수확 9칸이다.
- 공식 서버에서 실제 작물 5종 9개, 미성숙 밀, 전리품 생성, 내구도 1, 마지막 내구도 파손과 정리를 최초 부팅·`/reload`·같은 월드 재시작에서 확인했다. 실제 플레이어의 주/보조 손 사용, 키 유지 반복, 행운별 수량 분포와 2인 동시성은 헤드리스 시험이 증명하지 않는다.

## 패키징과 자동화 결함

- RC2 ZIP이 Windows `Compress-Archive` 때문에 `data\...`/`assets\...` 엔트리를 만들었고, 기존 테스트는 소스 폴더만 복사해 이를 놓쳤다. RC1/RC2 릴리스는 폐기한다.
- 패키저를 명시적 `ZipArchive` 엔트리 생성으로 바꿔 `/` 경로를 강제하고, 모든 엔트리 시각을 1980-01-01로 고정해 결정적 SHA-256을 만든다.
- 기존 서버 하네스는 첫 stdin 명령 앞 BOM으로 `/reload`가 실패해도 이전 점수값으로 통과하는 거짓 양성이 있었다. stdin을 사용하지 않는 로컬 RCON, 부팅별 99 sentinel, reload 완료 로그, 공식 JAR SHA-1/버전 검사를 추가했다.
- Oracle `javapath` 런처와 실제 JVM PID가 달라질 수 있어 `java.home`의 실제 실행 파일을 먼저 해석한다. 명령줄 식별자, run ID, PID JSON, 독점 잠금, watchdog, stdout/stderr 비동기 drain, 실패 로그 보존, 확인된 PID만 정리를 적용했다.

## 성능

틱 진입점에는 전역 엔티티 선택자가 없다. 검증기는 전체 틱 호출 그래프를 따라 bare/unbounded `@e`를 거부한다. 투사체 기능은 인챈트 사건에서 실행되고, 갈고리 앵커 선택은 활성 플레이어에게만 제한된다. 수확 낫은 사용 사건에서만 25단계 시선·9칸 작물을 검사하고 틱에서는 재무장 중인 사용자만 최대 10틱 처리한다. 고등 마법부여의 60책장 검사와 포션 정규화·병합은 각각 마법부여대·양조기 사용 발전 과제에서만 실행된다. 줄자와 분필 나침반은 trigger 함수에서만 계산·교체하며, 분필은 표시 중인 플레이어에게만 최대 100틱 동안 상수 개수 입자를 처리한다. 점프 발판은 플레이어별 발밑 두 블록을 상수 검사하고 구조가 맞을 때만 5칸 여유 공간과 적격 predicate를 평가한다.

## Realms 판정 범위

`pack.mcmeta`에는 명시적 `features` 블록이 없고 `/datapack list`의 `(world)`/`(세계)` 표시는 팩 출처다. 그러나 커스텀 인챈트 레지스트리를 포함한 월드가 클라이언트의 실험 기능 경고나 Realms 업로드·재시작 경로에서 어떻게 처리되는지는 전용 서버 성공만으로 증명되지 않는다. 실제 26.2 Realm 업로드와 재접속 시험 전에는 Realms 호환을 확정하지 않는다.
